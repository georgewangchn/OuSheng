# 多人 AI Coding 协作机制 — 方案基石

> 本文只定义**设计原则与逻辑边界**，不含实现代码。目的：在动工前，从第一性原理确认"逻辑上是否成立"。逻辑不成立则不做；成立才进入方案与开发。

---

## 0. 一句话定位

**这套多人 AI Coding 协作机制，是套在"AI Coding 这头㸸"鼻子上的牵引绳，不是㸸本身，也不是㸸栏、㸸车或牧场。** 绳必须能套在任何一头㸸上——机制与具体 AI Coding 工具（Claude Code / opencode / Codex / Pi / 人）解耦，不绑定任何单一实现。

牵引绳的价值不在于力气大，而在于**用最小的接触点，给出方向**。绳子越简单、越轻、越不试图替㸸使劲，系统越成功。任何想"帮㸸拉车"的设计冲动，都是失败的开始。

---

## 1. 五条设计原则（评判一切后续决策的标尺）

### 原则一：第一性原理

不从"友商怎么做""要不要加 Ontology/MQ/P2P"出发，只从一个根问题出发：

> 软件协作的本质是什么？——是在**认知容量有限**的前提下分工，分工后每个参与者**不可能也不需要**知道整个系统，只需要知道协作所必需的那一小部分。

由此推出唯一的基础事实：**对外协作所需信息 C，远小于内部完整状态 I（C ≪ I）**。这不是 AI 带来的新问题，是软件工程 60 年的旧铁律（信息隐藏 / 封装 / bounded context）。一切设计必须服从 C ≪ I，任何让全局承载 I 的设计（共享 Memory、全量知识库、中心大脑）从第一性原理即错误。

### 原则二：经得起逻辑推演与反事实推演

每个组件都必须能回答两问，答不上来就删：

- **正向：** 它解决的是 C（跨边界必需）还是 I（局部实现）？只有服务于 C 的才进入全局。
- **反事实：** 去掉它，系统还能不能协作？
  - 去掉"聊天消息"——仍能协作（状态还在）。→ 消息非核心。
  - 去掉"Task/Contract/State"——不能协作。→ **状态才是核心。**
  - 去掉 Ontology reasoner——5 人团队照常协作。→ 非 MVP。
  - 去掉消费方对真实接口的探测能力——协作漂移失效。→ **这是生死线（见 §4 C1）。**

反事实是这套系统最重要的自我证伪工具，优先于任何架构图。

### 原则三：契合控制论核心基石

本机制的内核是控制论。整套协作机制必须映射到经典控制元件，不引入与控制论冲突的新范式：

| 控制论元件 | 本系统对应物 |
|---|---|
| 参考信号 / setpoint (r) | **看板**（声明的目标工程状态：Task / Contract / Status） |
| 参考信号的量纲 | **接口标准**（Contract 字段的 schema —— 必须先钉死，如同控温前定义"温度"） |
| 被控对象 plant (P) | **agent + human 的 AI Coding 能力**（功率巨大、自带 actuation，**不建模**） |
| 传感器 (y) | 每个节点**自己的测试**（含打真实依赖的集成探针） |
| 误差 (e = r − y) | 看板声明的契约 与 本地现实实现 之差 |
| 控制器 (C) | **AI Coding 工具自带的收敛环**（写→测→改的 agentic loop，驱动本地 e→0；ASR 是其中一种实现，非必需） |
| 外生扰动 | **远端契约变更**（依赖方在看板改了契约，作为阶跃扰动注入我的环） |
| 监督控制 / 死区 | **人**只在误差大或歧义时介入（牵引绳只在方向错时拉紧） |

核心信条（控制论第一课）：**慢采样反馈 + 人的监督，可替代精确的 plant 模型。** 注意不是"反馈越强越好"——被控对象（AI Coding + 会改主意的人）是非平稳、非线性、结构未知的，高增益反馈会放大噪声、激发未建模动态，反而失稳。本系统的稳定不来自高增益，而来自**慢采样（C2 时标分离）+ 人监督（C3 死区）+ 离散慢修正**，这正是无 plant 模型下保稳的正确手段（低增益、慢、有监督）。因此不给㸸建模，只给它参考 + 反馈 + 方向仲裁。上一轮讨论试图建的一切"替 plant 干活"的机械（Contract 自动生成器、语义合并器、Ontology reasoner、中心验证管线），本质都是给 plant 建模，违背此信条，一律删除。

### 原则四：克制 —— 只做牵引绳

这是**核心定位，也是成功的关键**。判据只有一条：

> 每加一个东西，先问：这是"绳"还是"替㸸使劲"？替㸸使劲的，删。

- 看板内容天然很少——因为参考信号本就 ≪ plant 状态，这是第一性原理的结果，不是刻意精简。
- 工具**唯一必须做到极致**的，是两件事：**(a) 把看板内容呈现清楚；(b) 把系统间交互的接口标准定义好。**
- 其余——对看板与接口的理解、推理、测试——**全部交还给 agent + human 的 AI Coding 本能。** 之前的讨论恰恰弱化了这一特性，这是根本方向错误。AI Coding 的推理与测试能力是㸸的力气，工具不该抢、抢不过、也没必要抢。

克制不是能力不足，是控制论的正确姿态：**高增益反馈控制，本就不需要复杂的前馈模型。**

### 原则五：局部复杂，全局简单

- **局部（节点内部）：** 允许保留完整的代码、Memory、调试历史、推理过程、工具调用、失败尝试。这些对本地 agent 极有价值。
- **全局（看板 / 跨节点）：** 只承载 Task、Contract、Status、Owner、Dependency、Version、Event。
- 全局状态 = 各局部状态**面向协作的投影（Projection）**，**不是**各局部 Memory 的并集（union）。投影不是有损摘要（Summary），而是保留"外部依赖所必需信息"的语义压缩。

## 2. 核心逻辑命题

> **一块小的共享看板（reference）+ 一套定义良好的接口标准（量纲），足以协调多个 agent+human 编码环协作完成软件生产 —— 无需共享 Memory，无需中心契约验证，无需 Ontology。**

系统的最小单位不是 Prompt，是 Engineering Task；通信单位不是 Message，是 Contract / Event；状态单位不是 Chat History，是 Engineering State；知识单位不是 Shared Memory，是 Context Projection。

---

## 3. 最小系统（三件东西，多一件即违背原则四）

1. **共享看板** —— 分布式参考信号 + 可观测全局状态。卡片字段仅：`Task | Contract(接口定义) | Status | Owner | Dependency | Version`。每张卡片由其 Owner 节点签名（参考信号完整性）。
2. **接口标准** —— 看板 Contract 字段的 schema。工具**唯一必须钉死**的东西。
3. **每个节点 = 一个局部控制环** —— 参考 = 相关看板契约；plant = agent+human 的 AI Coding；传感器 = 自己的测试（含打依赖的集成探针）；控制器 = **AI Coding 工具自带的收敛环**（Claude Code / opencode / Codex / Pi 皆自带 写→测→改 的 agentic loop）。看板更新在环与环之间作为参考变更 / 扰动传播。全局环通过各局部环闭合。

**关于 ASR：非核心必需。** 局部收敛由 AI Coding 工具自身完成，本机制不重复造这个轮子。ASR 只是"其中一种节点实现"，其残余价值是可选的：(a) 一个"守规矩节点"的参考实现，示范协议如何落地；(b) 严格的收敛 / STUCK 检测 / 行为级传感，用于防止弱工具过早喊 `done`、把假 `verified` 写进看板污染下游——但这份纪律也可以塞进 skill 的 write 闸门（行为探针未过就不许写 `verified`），不一定非 ASR。核心三件物件 + 任意自带收敛环的 AI Coding 工具，即构成完整系统。

**明确不做：** Contract 自动生成器、语义合并器、Ontology、中心验证管线、P2P discovery / NAT / relay。它们要么在建模 plant，要么是过度设计，均违背原则三、四。

## 4. 成立边界 —— 三个充分条件（逻辑防线）

系统是一个耦合控制系统。以下三条件全部成立，则命题成立且系统稳定；**C1 破，则退化为开环，必然漂移 —— 此时不做。**

- **C1 可观测性（生死线）：** 消费方必须能对**真实**生产方接口闭环测量。前端 agent 按看板契约写码 + 集成探针打真后端，测出 y。契约漂移由消费方的环**自己检测**，不依赖中心验证器。若够不到真实接口（生产方离线），退化为 mock 开环，看板显式标记 `unverified`。
- **C2 时标分离（稳定性）：** 契约（外环参考）必须比本地代码收敛（内环）变化得**慢**。级联控制铁律：内环快于外环才稳。用"版本作锁存 + breaking 变更需人批作限速器"实现。契约变化过快，两环互相追逐将振荡。
- **C3 人注意力死区（可持续性）：** 人只在误差大或存在歧义时介入。非破坏性 / 加法变更由 agent 自主吸收（分层控制 + 误差幅度门控升级）。否则人被审批淹没，牵引绳变成缰绳。

**逻辑裁决：** 动工前，只需在纸面确认目标场景 C1 成立（接口可被真实探测）。成立即做，不成立即停。

## 5. 反事实兜底（最坏情况下命题不完全崩塌）

若实验发现"只给 Contract 不够，agent 必须要更多上下文"——命题**不失败，只降级**为：

> **默认按 Contract 协作；不足时按需最小化披露（Progressive Context Disclosure）。**

`Level 0 Contract → Level 1 接口细节 → Level 2 架构 → Level 3 实现 → Level 4 原始上下文`，默认 Level 0，仅在证据不足时逐级下探。对应安全领域的最小权限，此处为 **Least Context Principle**：agent 只获得完成当前任务所需的最小上下文。这同时优化 token、成本、隐私、认知负担、错误传播、上下文污染。

因此本方案在逻辑上具备鲁棒性：强命题成立最好，退化路径亦收敛，不存在"全有或全无"的脆断。

## 6. 通讯层放置 —— 通讯不是一个层，是边界采样

一旦想造"通讯中间件/消息层"，就已经在替㸸使劲。控制系统里，控制器与参考信号之间**没有通讯子系统**，参考信号只是被**采样（sample）**。因此本系统的"通讯"，就是在 agent loop 的两个边界点上，对共享看板做 read / write，没有独立的层。

### 6.1 一次 loop 迭代 = 一个控制周期（两个采样点）

```
loop 开始 ── read 看板 ──► 采样参考 r（我的契约 + 依赖方的契约变更＝扰动）
     │
     ├─ agent+human 编码 + 跑自己的测试 ──► plant 内部闭环，把本地误差 e→0
     │
loop 结束 ── write 看板 ──► 发布投影 y（新的 Contract / Status）→ 成为他人的 r / 扰动
```

两个采样点即足够，因为本地环在 plant 内部已自闭合（agent 自己的测试＝传感器，AI Coding 工具自带的收敛环＝控制器）。边界采样只负责**环与环之间的耦合**，不介入环内。这是采样控制（sampled-data control），也是最小接触点的牵引绳。

**关键：通讯层不放在 Memory（Memory 是局部 I，永不跨界），也不是像单机 ASR 那样开头一次性传入 prompt（那是开环）。它就是每周期对看板的边界读写。**

write 发布的不止一种卡。看板承载**两类卡**：**reference 卡**（setpoint——某方承诺提供、或某方需求的契约，生产方与消费方任一方均可发布，对应 §7.1 的 `proposed`）与 **output-status**（y——已 `verified` 的实际产出）。因此"write = 发布投影 y"是过窄的说法，准确表述为：**write 发布的是"reference 提议"或"verified 产出"，两者都必须通过 §6.5 的投影闸门（不漏 I）。** 消费方发布需求卡并不违背"局部复杂全局简单"——它写出的仍只是契约形状，而非自身的实现、Memory 或推理。

### 6.2 三个物件，对应控制论三件套（务必分清，勿混为一物）

| 物件 | 是什么 | 控制论角色 |
|---|---|---|
| **看板存储 store** | 一个共享 git 仓，每张卡一个文件，卡＝接口标准 schema | 参考信号总线（r 所在） |
| **执行器 actuator** | MCP server 或 CLI，仅两函数：`read_board` / `write_board` | 采样-保持的"线"（真正读 r、写 y 的 I/O） |
| **纪律 discipline** | skill / 协议文档 | 采样律（何时读、何时写、只投影） |

- **store** 首选 git 仓：version / 历史 / 签名白送（对应卡片的 Version 字段与 Owner 签名）。schema 即接口标准。
- **actuator** 是唯一真正跨工具通用的东西：`read_board(scope)→cards`、`write_board(card)→版本 CAS + schema 校验`。薄。opencode / claude / pi 皆可调用。
- **discipline** 是那两个采样点的行为载体：开工前 `read_board` 取本任务与依赖契约当作 spec；收工后 `write_board` 只吐 Contract / Status 投影，严禁吐源码 / Memory / 推理；版本冲突则重读、调和或上抛给人。

### 6.3 skill 与 MCP tool 不是二选一，是两层

- **skill 自身不存数据、不做 I/O**，它只规定"何时、怎么"。真正碰存储的必须是 MCP tool 或 CLI。
- 因此实现形态是 **skill 骑在 MCP/CLI 之上**，不能单独用 skill 完成通讯。
- skill 是"loop 开始读看板 / loop 结束写看板"这一采样律与投影律的可移植载体；跨工具时其可移植形态就是一份协议 markdown（等价于 AGENTS.md 类的规则文档）。

### 6.4 采样可靠性：hook 硬保证 > skill 软纪律

read 采样**必须发生**，否则本地环开环、在陈旧或空的参考上瞎跑。按工具原生能力选最硬的一档，全部调用同一个执行器：

- **Claude Code**：用 `SessionStart` hook 强制注入看板（read）、`Stop` hook 强制写回（write）——硬保证。
- **opencode / pi 等无等价 hook**：靠 skill 软纪律 + 每周期把看板投影注入上下文文件——软保证。
- 无论软硬，底层都打同一个 MCP / CLI 执行器。

### 6.5 投影闸门放两道（纵深防御，运行时守住 C ≪ I）

收工 write 只准吐 Contract / Status（C），严禁吐 Memory / 推理 / 调试（I）。否则看板腐烂为"AI 垃圾场"。两道闸：

- **软**：skill 指示"只投影"。
- **硬**：`write_board` 对接口标准 schema 做校验，不合规 / 超尺寸**直接拒**。

skill 会被偶尔忽略，schema 校验不会。硬闸门必须落在执行器里，这是运行时最关键的一道门。

### 6.6 落地清单 —— 只有 4 个薄物件

1. **git 仓当 store**，卡片＝ schema 文件。
2. **MCP server `board`**（或 CLI）：`read_board` / `write_board`（带版本 CAS + schema 校验）。
3. **skill `board-protocol`**：采样律 + 投影律 + 冲突处理；可移植形态为一份协议 markdown。
4. **（可选，Claude 专属）SessionStart / Stop hook**：硬保证采样，内部即调用 #2。

无 daemon、无 middleware、无任何组件持有业务状态。全是薄物件——这正是牵引绳的物理形态。

## 7. 生命周期与全局收敛 —— 补齐非稳态

§1–§6 定义了系统运行起来后的**稳态控制动力学**（环在跑、契约在流、局部误差被驱向零）。但完备性要求还回答三个**非稳态**问题：参考信号如何**诞生**、整个协作作为整体何时算**收敛或卡死**、依赖成环时**稳定性**如何保障。三者的解都不引入新机械，分别是一个状态机、一个归约函数、一个标准图约束。

### 7.1 参考信号的生成与生命周期（genesis）

稳态假设"契约已在板上"，但契约必须先诞生，且原始场景"前端需要更多接口"本质是**消费方驱动**地提出契约需求——因此 write 不能只建模为生产方的单向投影，需求侧同样能发起参考信号。

解 = **参考信号生成 + setpoint 仲裁**，落在看板卡的 `Status` 字段状态机上：

```
proposed ──► agreed ──► live ──► verified ──► deprecated
   ▲            │          │
   │(任一方发起) │(仲裁通过) │(实现完成、探针未过则回 live)
   └────────────┘
```

- **proposed**：任一方（生产方或消费方）均可创建一张 `proposed` 卡，声明"我承诺提供 / 我需要"的契约。这解决冷启动与消费方驱动。
- **agreed**：契约 Owner 与受影响方就该契约达成一致（跨方分歧＝ setpoint 冲突，由**契约 Owner 持仲裁权，消费方只能提议**；Owner 决断，必要时上抛更高层人类）。
- **live**：Owner 节点开始实现，契约成为下游可依赖的参考。
- **verified**：消费方的行为级集成探针通过（见 7.4），契约被确认与现实一致。
- **deprecated**：契约退场，依赖它的卡被标记需迁移。

整个生命周期只是 `Status` 一个字段的状态迁移，零新机械。诞生、协商、派发、退场全部在此闭合。

### 7.2 全局收敛与活性判据

最深的完备性要求：**局部收敛 ≠ 全局收敛**。每个节点各自满足本地参考，拼起来未必整体一致可跑。单节点有 `done / stuck` 语义（任何自带收敛环的 AI Coding 工具都有），多节点必须有对应的**全局**信号，否则没人知道"协作作为整体是否完成"。

解 = **看板上的纯归约函数（reduction over cards）**，是单节点收敛在全局的聚合：

- **GLOBAL CONVERGED** ⟺ 所有契约 `status = verified` **且** 所有消费方集成探针通过 **且** 无 `proposed / broken` 卡悬挂 **且** 依赖图全部满足。
- **GLOBAL STUCK** ⟺ 某契约 `broken` 或 `stuck` 持续 N 个周期，**或**检测到死锁（A 等 B 的契约、B 等 A 的契约，互相阻塞），**或**依赖成环（见 7.3）。

此判据是看板状态的一次 reduce，不需要 daemon、不需要中心大脑，任何节点或人都可在本地对看板计算得出。全局可观测性由此闭合：人看一眼看板即知全局是否收敛、卡在哪张卡。

### 7.3 依赖图约束为 DAG（保障多环稳定）

C2（时标分离）假设依赖存在级联层级。但依赖**成环**（A↔B 互依）会打破级联假设——即便契约变化足够慢，仍可能出现极限环振荡，C2 救不了。

解 = **看板的依赖图强制约束为 DAG**。检测到环则判为 `GLOBAL STUCK` 并标记，交由人打断（拆分契约或引入更慢的共享仲裁点）。判环是标准图算法，在看板数据上直接计算，无新增机械。

### 7.4 硬化 C1：传感器必须是行为级

补强生死线 C1：消费方的传感器必须测量**行为**（真实交互是否产出所需结果），不能只做 schema 形状校验。否则"形状对、语义错"的实现能骗过下游——契约状态显示 `verified`，实际行为却是错的。因此 7.1 中 `live → verified` 的迁移条件，必须由行为级集成探针把关，而非仅结构一致性。

### 7.5 完备性结论

- **稳态控制动力学（§1–§6）：完备且无冗余**——闭环每个元件（参考、误差、控制器、执行、传感器、扰动、稳定、采样、人监督、全局可观测）均有定义，且逆向测试中每条皆承重。
- **非稳态（§7）：由生命周期状态机、全局收敛归约、DAG 约束补齐**——覆盖参考信号从诞生到退场的完整生命周期、全局收敛与活性、多环稳定。

至此，正向（诞生→运行→收敛→退场）与逆向（去掉任一件即坏）双向完备，且全部解都止于薄物件，未违背牵引绳定位。

## 8. 系统不保证什么 —— scope 边界（完备设计的诚实声明）

一个完备的设计必须写明它**不保证什么**，否则使用者会对它抱有它给不了的期待。控制论给出一条硬边界：

> **你可以完美地跟踪一个错误的参考信号。**

因此本系统的能力边界是：

- **保证：一致性 + 向参考收敛。** 各局部环收敛到看板声明的契约；全局归约可判定整体是否一致、是否卡死；契约与现实的偏差被消费方的行为级探针检出并驱动修复。
- **不保证：意图正确。** 若被各方 `agreed` 的契约本身是个坏设计，系统会把所有人**一致地、忠实地**收敛到这个坏契约。工具只保证"㸸去你指的方向、且各环彼此一致"，**不保证你指的方向是对的**——那是人 / 产品的判断，位于控制环之外（正是牵引绳定位：人握绳定方向，工具只确保㸸忠实前行）。

由此还有两条须显式标明的诚实边界：

- **`unverified` / 探测不到的依赖，会永久阻挡 GLOBAL CONVERGED。** 这是**故意的诚实信号**（你确实无法确认它能跑），不是死锁 bug。系统宁可如实报告"未验证"，也不谎报收敛。
- **§7.3 的"依赖成环即判 STUCK"是保守安全近似。** 慢且阻尼良好的互依在控制论上未必失稳，但为保持规则简单、避免误判，本系统一律保守地要求 DAG、把环交给人打断。这是有意识的取舍，非"环路理论上必然失稳"。

牵引绳只负责方向的忠实传导与全局一致，不替人决定目的地是否值得去。承认这条边界，方案才既完备又诚实。
