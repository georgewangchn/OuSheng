## 2. 发布条件（2026-09-18 推演全文）

### 2.1 三条件推导

一个发布出去的任务要成立，必须**可寻址**（落在某个系统）、**可问责**（有主，或显式标记待认领）、**可判定**（信息够执行者开工、够验收者判定）。缺一即不可执行——现状的反面不是"所有人都会执行"，而是"**没人执行**"：无主单不进任何人的 `context me`，静默孤儿。

### 2.2 状态即门槛（信息门槛挂状态，不挂创建）

反事实：信息门挂创建 → 建单摩擦 → 逼出"待定"式造假（description 填垃圾过门）。故 `backlog` 不查（先记账），`ready` 起查按类型最小信息集，`done` 必有证据（C1）。

### 2.3 active 无主硬门的统一（2026-09-18 定位推演）

- 三态定义皆为"有人正在推进"：doing 有人在干、testing 有人在验、blocked 有人会回来解阻。无主 = 语义矛盾，且没有任何执行者的 context me 会收到它。
- 合法场景（换人验证、换人接手）走 `work assign` **换主**，从不需要清空主 → 无为 testing/blocked 开特例的理由。
- 反事实：开特例 → 多分支多解释，还给"清空主逃避问责"留缝。
- 硬门定位：跨主体伤害（无人收到 ≠ 无害，是协作假象），与 C1/C2 同族；写路径硬门 + converge BLOCKER 双层。

### 2.4 分层强制

硬门只挡"进行中无主"；其余走曝光——converge：active 无主 = BLOCKER、backlog/ready 无主 = warning「待认领」、ready+ 缺信息 = warning。「信息够不够」有判断成分，硬门会逼出造假（同 2.2 反事实）。

### 2.5 四路判决（无主/信息不全信号）

不进 `context me`（注入面最小化——执行者不需要知道不归他的单）；进 `work list` + converge。`view system` 只列 active，不是无主信号面（写路径已杜绝 migrate 之外的无主 active）。

### 2.6 migrate 与无主 active

v1 `live` 卡迁移为 `doing`；owner 解析失败标 `migration_status: needs_resolution` 且无主 → converge BLOCKED（有意：无主 active 不可执行）。仅 `live` 卡——`proposed`/`agreed` 落 ready/backlog，无主仅 warning「待认领」。指定解阻路径 `migrate resolve-owner` 与 Service.Update 同门（active 且无 assignee 拒绝；role-only 解析会留下无主 active，必拒）。

### 2.7 修复记录

- `3b3a76a`：文档改真（`view system` 假承诺删除）+ `--unassigned` 隐含 open + active 门从 doing 扩三态。
- `5acd684`：二次 review——resolve-owner 补 active 门（role-only 绕道洞）+ `TestMigratedNeedsResolutionBlocks` 换真链锁（converge 不读 MigrationStatus，手构 item 与 doing 用例等价，锁不住链路）。
- **教训（入 §6 教训集）**：同语义门必须覆盖全部写径——扩门时只查了 Service.Update，漏了 migrate 直写。

## 4. 两段式配置 join（2026-09-15 三轮推演）

### 4.1 死法机理（永久出局）

- **join 审批门**：无效门——有 push 权者拦不住（他能直接 push），无权者本来进不来（没 push 权注册了也没用）；federation 退回中心规划。
- **注册表自动清理**：破坏性动作须 human。
- **responsible-human 活跃度检查**：语义，机器测不了。
- **Web 配置中心/注册服务**：零基础设施违例。
- **repos.yaml 集中上绳**：本机路径非共识，状态/共识两分判出局。

### 4.2 时间轴接力

join 管初始注册（事实）→ design 管拓扑演化（共识，动土先起 design）→ work 管执行（状态），三段无缺口。

| system / assignee | 可寻址/可问责门 + active 门 | 留（卡） |
| contract / evidence / human_ack | C1 / C2 | 留（卡） |

| title / type / schema_version / depends_on | 可读性 / 类型门 / 严格解码 / 依赖审计 | 留 |
| progress | 收尾信号（reported，basis 必填） | 留（引导） |
| acting_role | 问责上下文（work assign 消费） | 留（引导） |

## 8. 越位事故与身份裂缝裁决（2026-09-20，TASK-007）

**事故**：226（human 型 actor，PM）的 AI 会话自建单 TASK-007 → 自侦察生产集群 5m46s（kubectl/helm/registry）→ 自挂证据 → 自改派。绳上全程合法。靠 human 扫视才发现。

**根因三层**：
1. **身份层裂缝（最深）**：绳的信任模型是"actor 类型 = 键盘后是谁"。多机部署下，human 型 actor 的机器上跑 AI 会话 = AI 披 human 皮，所有类型门（C2 ack / design decide / F4 授予）对其失明；activity 审计无法分辨人还是 AI（问责链作废）。
2. **语义层边界（设计使然）**："侦察算执行"是语义分工判断，绳的卡点不变式明写不卡语义。越位被拦靠 human 扫视——这是设计闭环，不是绳失灵；**失灵的是"越位后绳上无痕迹"**（= 层 1）。
3. **结构层放大器**：中枢机 AI 手握生产权限 + 单子自建 + human 身份零卡点；且 assignments 的 executor 图在事故前无任何消费者（纯装饰）。

**裁决**：
- **human 挂 active 执行单 assignee = warning「决策位坐执行位」，不设硬门**——单人项目 human 亲自干活是合法常态，硬门会误伤；多机 PM 场景靠曝光让人扫视有信号（分层强制镜像：硬门挡"无主"，曝光挡"错位"）。
- **active 单 assignee 在该 system 无 executor assignment = warning「跨域执行」**——仅当该 system 已有 executor 图（存在行）才查，空图 = 未排班不查（避免早期项目噪音）。executor 图自此有第一个消费方。
- **PM 机 AI 会话必须用独立 agent 型 actor**（responsible-human = 该 human，F4 门通过），human 型 me 只留给终端亲操；`adapter install --actor` 落 AI 身份进 ousheng.json。此为车队纪律非产品门（同机多窗口协议 join 已有，无需新代码）。

**反事实**：若把两条警告升级为 BLOCKER——单人项目（human 唯一执行者）永远 BLOCKED，converge 信号失去分辨力，重蹈"waiting 算 BLOCKED"覆辙；若不修身份层只修曝光——下次事故形态变为"agent 型越权执行但账面干净"，曝光照旧抓不到，故车队身份纪律与产品曝光缺一不可。

**锁**：`TestHumanAssigneeActiveWarns` / `TestCrossDomainExecutorWarns` / `TestAdapterInstallActorOverride`。

### §8.1 本体覆盖矩阵（2026-09-20 系统性推演）

本体四层——词汇（严格解码）/ 类型（actor.type、responsibility）/ 门（写路径）/ 审计（converge 派生谓词）——**无第五层推理机**：没有任何组件从本体推出"这个动作违职责"，converge 是批量事后审计不是动作时推理。

四公理：A1 绳只能治理流经它的写；A2 卡状态合法性不卡语义（职责=语义）；A3 actor.type 语义 = 键盘后是谁（部署假设，非验证事实——绳不验也不能验）；A4 system 是逻辑域非物理机。

职责覆盖三档：
- **写路径硬门档（真 100%）**：C1/C2/F4/active 门/状态机/问责 human 型/assignee 存在性——只覆盖"跨主体伤害与状态合法性"
- **事后曝光档**：决策位坐执行位 / 跨域执行（ee6b8e9 起）
- **0% 档（原理不可修到 100%）**：绳外动作（A1）与语义分工判断（A2）——靠人扫视，这是牵引绳的本体论决定不是 bug

职责遵循的物理上限 = 流经绳的写 100% 卡死 + 流经绳的痕迹 100% 曝光 + 身份真实（车队纪律）。

### §8.2 待裁缺口三件（记判据防丢）

| 缺口 | 现状 | 判据（真实出现才动） | 候选修法 |
|---|---|---|---|
| 机器↔演员绑定缺失 | git committer 从未与 actor 做交叉验证；AI 穿号只靠车队纪律 | 再现 AI 穿号事故，或同机多操作源需区分且 committer 面不够用 | git committer × actor 交叉验证（converge 审计档起步，不进写路径） |

## 9. 设计撤回终态裁决（2026-09-20，atw-approval-notify 事故）

**事故**：PM 取消 MQ 推送需求要撤回 draft 设计，发现** draft 无终态**——supersede 只收 agreed（draft 无权威可转移），唯一出路是手改 frontmatter 贴「已撤回」横幅 + 手切 related_items 消超前曝光警告，被迫绕绳两次（d05ea98/571d573）。无合法路径的绕过比有门的绕过更糟：它把「手改 frontmatter」常态化。

**裁决**：
- 补第四态 **withdrawn**（撤回终态）：`design withdraw <topic> --actor <owner-or-human>`。
- **这不是拍板门**（与 decide/supersede 的 human 门区分）：draft 从未获得权威、无共识可转移，收回自己的提案不构成跨主体影响——owner 即可操作（agent 可撤自己的）；非 owner 的 agent 撤别人的 draft = 跨主体伤害，拒（镜像 F4 哲学）；human 手不卡。
- 字段铁律：withdrawn 须 `withdrawn_by`、禁 `superseded_by`（无权威可转移）与 `decided_by`（从未拍板）。
- 联动零改动即生效：pending_reviews 与 converge 超前曝光都只认 `draft`，withdrawn 结构性出局——226 当日手切 related_items 的动作从此不需要，死方案持活链接属档案事实不是噪音。

**反事实**：若允许 agreed→withdrawn——已获共识的方案被 owner 单方面静默收回，下游按共识开工的工作失去权威依据且无继任者指认，重蹈「知识断链」；故 agreed 的关闭必须走 supersede（human 门 + 继任者存在）。若 withdraw 也设 human 门——agent 发起的 draft（PM 发单流程 design 先行，agent 可起草）被废弃时同样无路可走，回到手改横幅。

**锁**：`TestDesignWithdraw` / `TestDesignWithdrawnValidation` / `TestWithdrawnDesignNoAheadWarning`。

## 10. sync 收尾推送与协议段命令速查（2026-09-20，BUG-001 上绳事故）

**事故**：226 的 ui 会话发现 mlake 问题（Flink REST NodePort 31083 间歇超时），发单全程证明绳在工作——plugin 正常 sync、MCP `query_work_items`/`report_bug` 调通、BUG-001 连证据一起落地（detected_by: ui）。但用户观感是「没上绳，ousheng 没任何反应」。解剖出两个真缺口：

1. **CLI 语法不可发现**：AGENTS.md 协议段只讲三时机不给命令表。AI 猜 `ousheng bug report`（语法其实对）→ 见 usage 退回 → 疑心 → `--help`/`-h`/grep 二进制/sqlite 挖表，绕两分钟最后靠 MCP 工具发单。协议给了时机没给词汇，等于指了方向没给缰绳。
2. **收尾不推送**：`ousheng sync` 只 pull 不 push，plugin 时机③只跑 converge。BUG-001 自动提交后烂在 226 本地（ahead 2），全舰队不可见直至人工推送。多机车队里未推送的工单 = 不存在的工单。

**裁决**：
- `sync` 在 pull 成功后 **push 收口**（先拉齐再推，分叉态不推）；软失败——push 失败仅提示不阻塞索引与上下文，无未推提交静默。推送不进写路径（写路径 push 会在冲突时阻塞合法写入，违反「卡 agent 的写不卡 human 的手」的镜像边界）。
- AGENTS.md 协议段补**命令速查**（bug report/todo/work list/show/update/assign/context me/converge→sync），机器中立禁串不变（锁 `TestAgentsSectionIsMachineNeutral`）。命令词汇是绳的缰绳不是牛的活——协议层引导，非语义代办。
- 时机③ 文案补 `sync` 推送收口；plugin 不动（session.idle 每次响应后都触发，sync 含网络操作挂上去就是每 loop 轮询，违反三时机铁律；时机① 的 sync 已保证下一会话启动时兜底推送）。

**反事实**：若 push 进写路径——两机并发写后先后 push，后推者被拒，写路径报错但 YAML 已落盘，用户面对「单建了但命令失败」的中间态；sync 收口把推送的冲突面收敛到 pull 之后，失败可重试无副作用。若命令速查放进 plugin 注入——每 session token 开销，且 AGENTS.md 本就是 opencode 的 rules 载体，零额外成本。

**锁**：`TestCLISyncPushesLocalCommits`（事故形态复现：写路径自动提交 → sync → 远端必须收到）。

**关联**：LiteLLM 网关（192.168.1.12）间歇断连同日志可见——基础设施问题，另案，不在绳上修。

## 11. 工作区全局放行裁决（2026-09-20，external_directory 权限询问事故）

**事故**：224/225 每次 opencode 启动都弹 `/data/kanban`（工作区）访问权限询问。根因三层：opencode `external_directory` 默认 `ask`；TUI 的 "always" 放行**只活当前会话**（不落盘）；工作区在代码仓之外必然触发外目录门。

**裁决**：`adapter install` 第六步——把 `permission.external_directory[<workspace>/**]="allow"` 合并进**全局配置** `~/.config/opencode/opencode.json`。要点：
- **落点只能是全局**：工作区路径是机器本地信息，五件套全是入库机器中立资产放不下路径；项目配置层（根/`.opencode/` opencode.json）入库会跨机冲突。
- **合并只增不删**：key=工作区路径模式（自标识），既有键全保留；首次改动前备份 `.bak-ousheng`；`permission`/`external_directory` 非对象结构或 JSON 解析失败（JSONC 等）→ 拒绝改写、给人话指引——**不碰用户配置**；软失败不阻塞 install（权限询问是摩擦不是阻断）。

**反事实**：若把路径塞进项目 opencode.json——224 是 `/data/tide/kanban`、225 是 `/data/kanban`、本机是 `/Users/...`，同一仓克隆到别机即冲突，重蹈「协议外置分发 = 漂移死法」；若不修——每个会话人工放行一次，零摩擦上绳的承诺破产，用户迟早习惯性点掉所有权限弹窗（安全训练负向）。

**实证**：`opencode debug config` 确认 `.opencode/opencode.json` 确实被加载（文档 precedence 清单未列，1.18.31 实测有效）——五件套 MCP 配置不白写；权限解析为空印证默认 ask。

**锁**：`TestAdapterInstallGrantsWorkspacePermission`（预置 provider 合并保留 + 幂等 + 非对象结构软失败）。既有六个 install 测试补 `t.Setenv("HOME")` 隔离——install 现在写全局配置，不隔离会污染真实机。
