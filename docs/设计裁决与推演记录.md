## 1. 全局审计结论（2026-09-18 系统性推演 + 重推演）

### 1.1 卡点不变式（从全部写路径门与"不卡"清单中归纳）

> **卡 agent 的写，不卡 human 的手；卡跨主体伤害与状态合法性，不卡语义与质量。**

- 所有写路径门（C1/C2/decide 门/active 门/F4/resolve-owner 门）都长在 CLI 写径上；human 手改 YAML 可绕过是有意设计，外防线 = git 审计。
- "不卡"清单同样齐整且各有记录在案的理由：信息完备性不设硬门（机器测不了语义，硬门逼出"待定"式造假）；声部伪造不机器校验（advisory，git author 对账）；evidence 除 git_commit 外不验真（传感器属消费方局部环，绳建验证管线 = 替牛使劲）；architecture 无门禁（文档错误成本 = 人看见改回来）。

## 2. 发布条件（2026-09-18 推演全文）

### 2.1 三条件推导

一个发布出去的任务要成立，必须**可寻址**（落在某个系统）、**可问责**（有主，或显式标记待认领）、**可判定**（信息够执行者开工、够验收者判定）。缺一即不可执行——现状的反面不是"所有人都会执行"，而是"**没人执行**"：无主单不进任何人的 `context me`，静默孤儿。

### 2.2 状态即门槛（信息门槛挂状态，不挂创建）

反事实：信息门挂创建 → 建单摩擦 → 逼出"待定"式造假（description 填垃圾过门）。故 `backlog` 不查（先记账），`ready` 起查按类型最小信息集，`done` 必有证据（C1）。

### 2.3 active 无主硬门的统一（2026-09-18 定位推演）

- 三态定义皆为"有人正在推进"：doing 有人在干、testing 有人在验、blocked 有人会回来解阻。无主 = 语义矛盾，且没有任何执行者的 context me 会收到它。
- 合法场景（换人验证、换人接手）走 `work assign` **换主**，从不需要清空主 → 无为 testing/blocked 开特例的理由。
- 反事实：开特例 → 多分支多解释，还给"清空主逃避问责"留缝。
- 硬门定位：跨主体伤害（无人收到 ≠ 无害，是协作假象），与 C1/C2 同族；写路径硬门 + converge BLOCKER 双层。

### 2.4 分层强制

硬门只挡"进行中无主"；其余走曝光——converge：active 无主 = BLOCKER、backlog/ready 无主 = warning「待认领」、ready+ 缺信息 = warning。「信息够不够」有判断成分，硬门会逼出造假（同 2.2 反事实）。

### 2.5 四路判决（无主/信息不全信号）

不进 `context me`（注入面最小化——执行者不需要知道不归他的单）；进 `work list` + converge。`view system` 只列 active，不是无主信号面（写路径已杜绝 migrate 之外的无主 active）。

### 2.6 migrate 与无主 active

v1 `live` 卡迁移为 `doing`；owner 解析失败标 `migration_status: needs_resolution` 且无主 → converge BLOCKED（有意：无主 active 不可执行）。仅 `live` 卡——`proposed`/`agreed` 落 ready/backlog，无主仅 warning「待认领」。指定解阻路径 `migrate resolve-owner` 与 Service.Update 同门（active 且无 assignee 拒绝；role-only 解析会留下无主 active，必拒）。

### 2.7 修复记录

- `3b3a76a`：文档改真（`view system` 假承诺删除）+ `--unassigned` 隐含 open + active 门从 doing 扩三态。
- `5acd684`：二次 review——resolve-owner 补 active 门（role-only 绕道洞）+ `TestMigratedNeedsResolutionBlocks` 换真链锁（converge 不读 MigrationStatus，手构 item 与 doing 用例等价，锁不住链路）。
- **教训（入 §6 教训集）**：同语义门必须覆盖全部写径——扩门时只查了 Service.Update，漏了 migrate 直写。

## 3. SQLite 定位（2026-09-13 推演裁决，防"零读者部件"复发）

- 产品查询路径默认 memory（零基础设施模式）；sqlite 是派生索引。
- 树内消费者 = S5 等价测试（交叉验证 oracle）；树外用途 = 只读 SQL 查询面（`ousheng index rebuild` 后查 `.ousheng/cache/index.db`）。

## 4. 两段式配置 join（2026-09-15 三轮推演）

### 4.1 死法机理（永久出局）

- **join 审批门**：无效门——有 push 权者拦不住（他能直接 push），无权者本来进不来（没 push 权注册了也没用）；federation 退回中心规划。
- **注册表自动清理**：破坏性动作须 human。
- **responsible-human 活跃度检查**：语义，机器测不了。
- **Web 配置中心/注册服务**：零基础设施违例。
- **repos.yaml 集中上绳**：本机路径非共识，状态/共识两分判出局。

### 4.2 时间轴接力

join 管初始注册（事实）→ design 管拓扑演化（共识，动土先起 design）→ work 管执行（状态），三段无缺口。

## 7. 字段移除轴裁决（2026-09-18，P2）

**问法（R9 扩展到 WorkItem）**：逐字段问"删了它，LLM + git + 现有机制顶得住吗？顶不住的必须回答'卡哪个门'或'引哪条导'"。新标准：**字段辩护 = 被某个门消费（卡），或被判为方向信号（引导）并写明辩护词；四路展示不是充分辩护**。

| 字段 | 卡点/引导 | 裁决 |
|---|---|---|
| status / revision | 状态机 + CAS | 留（卡） |
| system / assignee | 可寻址/可问责门 + active 门 | 留（卡） |
| contract / evidence / human_ack | C1 / C2 | 留（卡） |
| accountable_human / detected_by | 问责链（F4 / bug 溯源） | 留（卡） |
| description / target_version | 可判定性门（类型最小信息集） | 留（卡） |
| title / type / schema_version / depends_on | 可读性 / 类型门 / 严格解码 / 依赖审计 | 留 |
| progress | 收尾信号（reported，basis 必填） | 留（引导） |
| acting_role | 问责上下文（work assign 消费） | 留（引导） |
| migration_status / legacy_owner | v1→v2 过渡件，resolve 后自清 | 留（过渡） |
| priority / due_on | **无门消费**；PM 分诊方向信号，四路已接通 | **留（引导）**：辩护词 = 分诊优先级的方向信号，弱但真实；删除成本（迁移+四路拆除）大于保留成本。若真实使用中无消费（PM 从不看），下轮移除轴再审 |

**结论**：字段集全部通过，但"字段只增不减"的趋势由本裁决封口——新增字段必须声明卡点或引导职能（AGENTS.md 铁律）。
