# Super-agent 和 OuSheng 怎么选

这两个东西最近老被放在一起比，其实不是竞品。Super-agent 管的是跑得动，OuSheng 管的是算不算数。一个是执行层，一个是治理层，大多数团队两个都用得上，只是先后顺序不一样。

## Super-agent：解决人盯不过来的问题

一个人同时推五件事，得开五个会话分别盯；群里报了个 bug，得有人 @ 它才动；本地环境一关机，任务就停了。

Super-agent 干的就是把这些接过去：多任务并行、主动响应、持续在线。人只定目标和验收，调度和执行交给 AI。DeepSeek 10 月 31 日开源，MIT 协议，跑在自家 Harness 框架上。

优点：

| 优点 | 说明 |
|---|---|
| 并行吞吐高 | 多个 Worker 同时干活，互不阻塞，p95 比单会话快近一倍（自报合成数据） |
| 主动 | 群聊报 bug、CI 挂了，不用 @ 它，自己发现自己动 |
| 跨渠道连续 | IM、GitHub、邮件，同一个 Agent，不用切会话补上下文 |
| 持久 | 存算分离加 Watchdog，电脑关了任务还在跑，卡死能自愈 |
| 开源 | MIT，代码在 GitHub，可以自己改 |

局限：

| 局限 | 说明 |
|---|---|
| 不是生产软件 | 官方自己说这是研究原型，别直接上生产 |
| 权限粗 | 只有 off/observe/auto 三档，没有"这件事该不该由它做"的细粒度 |
| 日志不是账本 | Trajectory 记录发生过什么，但不回答哪份产物算数、谁批准的 |
| 冲突靠自觉 | 多个 Worker 撞车，靠它们都订阅同一个 Thread 自己发现 |
| 成本高 | 单次运行 cache token 两千多万，拿 token 换速度 |
| 只支持单仓 | 目前只面向一个 GitHub 仓库 |

## OuSheng：解决算不算数的问题

换一种情况。几个 Agent 同时改一个仓库，两份文档都在改，说不清哪份是真的；方案改了三版，最后对不上拍板的是哪版；出了问题要回答"这个改动谁批准的"，答不上来。

这些 Super-agent 不管。OuSheng 管：一件事只有一个主人，方案生效必须有人类签名，任何产出都能摸回来处。它自己不执行任何任务。

优点：

| 优点 | 说明 |
|---|---|
| 消灭多头管理 | 受管辖的文档、方案、任务只有一个认领主体，机器自动扫出没人管的 |
| 人类签名是硬门 | 方案从草稿到生效必须记录人类决策者，Agent 不能自己改状态，这是代码里的硬校验，不是提示语 |
| 不造假真相 | 数据在你们自己的系统里，OuSheng 只做投影，记录谁、何时、定了哪版 |
| 出处可查 | 任何产出能顺着记录摸回它的来处 |
| 轻 | 不跑任务不占算力，纯治理层 |

局限：

| 局限 | 说明 |
|---|---|
| 不替你干活 | 不执行代码不跑测试，不是 Agent 框架 |
| 需要人参与 | 拍板必须人来做，想要全自动的帮不了 |
| 小团队可能用不上 | 十人以下、没审计压力的，上它属于杀鸡用牛刀 |
| 早期项目 | 生态和文档还在建 |

## 对比

| 维度 | Super-agent | OuSheng |
|---|---|---|
| 解决的瓶颈 | 人的注意力：同时只能盯 3–5 个会话 | 决策的权威性：哪份算数、谁批准 |
| 优化目标 | 吞吐与延迟 | 可追溯与不可抵赖 |
| 人的角色 | 定目标、验收结果 | 授权、签字、负责 |
| 不做什么 | 不回答谁批准的 | 不替你执行任务 |
| 成熟度 | 研究原型（官方声明） | 早期项目 |

## 怎么选

用 Super-agent：

- 一个人同时推多个任务，每个都得开个会话盯
- 希望群里报 bug、CI 挂了，AI 自己就动起来
- 团队小、没审计压力，快就完事了

用 OuSheng：

- 多个 Agent 或多个人同时改一个东西，经常吵"哪份是真的"
- 方案改来改去，最后说不清哪版是拍板的
- 改动要进生产、要过审计，得能回答谁批准的

两个都用：

- 已经在用 Super-agent 或类似执行引擎并行干活
- 但它的产出要进生产、要对账，需要落地前有个闸

组合的方式很直接：Super-agent 负责跑，OuSheng 在它提交变更前问一句，这件事有人拍过板吗，没有就停。

## 最后

Super-agent 让 AI 多干活，OuSheng 让 AI 干的活算数。选之前先想清楚，你现在缺的是效率，还是责任。
