# OuSheng 多机多窗口使用指南

> **场景**：N 个系统（各自独立 Git 仓库、分布在不同机器）+ 每台机器一个 opencode 窗口（AI coding）+ 可选产品经理（不写代码，只发需求、看进展、拍产品板）。
>
> 本文以 **4 系统 × 4 机器 + 1 PM** 为例。人名、系统名均为示例，按需替换。
>
> 前置阅读：`docs/quick-start.md`（单机 5 分钟入门）。

---

## 0. 总览：拓扑与核心规则

```
                        GitHub
        ┌──────────┬─────┴──────┬─────────────┐
   repo:data-svc  repo:ops-svc  repo:admin-api  repo:admin-ui    ← 4 个代码仓（照旧，互不相干）
        └──────────┴─────┬──────┴─────────────┘
                       │
              repo: ousheng-board   ← ★ 第 5 个仓：上下文仓（唯一通讯中心）
                       │
       ┌───────────────┼───────────────┬──────────────┐
   机器A clone      机器B clone     机器C clone     机器D clone（+ PM 机器 clone）
   data-svc         ops-svc         admin-api       admin-ui
   opencode 窗口    opencode 窗口   opencode 窗口    opencode 窗口
   身份=data-dev    身份=ops-dev    身份=api-dev     身份=ui-dev
```

**四条规则**：

1. **上下文仓是唯一的通讯中心**。机器之间零直连，只对 `ousheng-board` 仓 push/pull。代码仓之间也零通讯。
2. **代码仓零侵入**。代码仓里唯一多出的是 `.opencode/plugins/ousheng-sampler.ts`（十几行）和 AGENTS.md 里的纪律段，不进构建。
3. **AI 干全部体力活**。建单、更新状态、挂证据、收敛检查、推送，全部由窗口里的 AI 执行；人只拍板、只提问。
4. **人只出现两次**：一次性安装 + 破坏性变更时敲一次 `--ack`。

## 1. 角色规划表

> 本表是规划参考，**不是配置清单**——实际注册由各机在阶段 1 join 时自助完成（联邦式：拓扑是涌现的，不是预先规划的）。

| 机器 | 窗口身份 | 类型 | 绑定系统 | 职责 |
|---|---|---|---|---|
| A | `data-dev` | agent | data-svc | 数据服务开发 |
| B | `ops-dev` | agent | ops-svc | 资源管理开发 |
| C | `api-dev` | agent | admin-api | 管理后端开发 |
| D | `ui-dev` | agent | admin-ui | 管理前端开发 |
| 任意 | `lead` | human | — | 负责人：技术拍板、全局总览 |
| 任意 | `pm` | human | — | 产品经理：发需求、看进展、产品拍板 |

## 2. 阶段 0：配置中心（任意一台机器，只做一次，三行）

系统、agent **都不在这里配**——中心只出「项目地址」这个锚点，其余全部由各机自助上绳：

```bash
# 0.1 建仓 + 立项
mkdir ~/board && cd ~/board && git init
ousheng init

# 0.2 你的身份（推荐顺手做：decide 拍板门 / accountable / agent 问责都锚在
#     第一个 human 上；也可省略，由第一台 join 机涌现出 first human）
ousheng me lead --name 负责人

# 0.3 推上 GitHub，成为所有机器的共同 remote
git remote add origin git@github.com:<org>/ousheng-board.git
git push -u origin main
```

可选：中央仓 README 写一行指针（新机 agent 看到即知怎么加入）：

```markdown
本项目用 OuSheng 上绳。新机器/新窗口：clone 本仓后运行 `ousheng join`，按协议自助上绳。
```

> 为什么这么少：注册表是 append 型文件，谁写都一样（信任边界 = git push 权，本就如此）；
> 预先规划全部系统反而隐含「拓扑在配置时已知」的错误假设——真实团队拓扑是长出来的。

## 3. 阶段 1：每台机器自助上绳（时机零，约 5 分钟）

每台机器跑 `ousheng join` 打印协议，按协议走（本机 opencode 问答或人手工执行均可——协议与 CLI 同版本，`join` 输出即权威）：

```bash
# 1.1 装 CLI + 克隆上下文仓（ousheng 源码一次性克隆）
git clone git@github.com:georgewangchn/OuSheng.git ~/ousheng-src
go build -o /usr/local/bin/ousheng ~/ousheng-src/cmd/ousheng
git clone git@github.com:<org>/ousheng-board.git ~/board
cd ~/board

# 1.2 打印时机零协议，按步执行
ousheng join
```

以机器 C（admin-api 的 agent 窗口）为例，协议落地后的实际命令：

```bash
# 1.3 注册 agent 身份（顺序锁：先 team add 再 me——me 对新 actor 恒建 human 型）
ousheng team add api-dev --type agent --responsible-human lead --role backend --system admin-api
ousheng me api-dev

# 1.4 选择系统：先看清单再选（清单空才创造——防命名漂移）
ousheng system list
ousheng system add admin-api --name 管理后端    # 仅当清单里还没有时

# 1.5 本机系统→代码仓映射：git_commit 证据会去这里验证
ousheng repo set admin-api ~/code/admin_api

# 1.6 环境变量（写进 ~/.zshrc 或 ~/.bashrc）
export OUSHENG_BIN=ousheng
export OUSHENG_DIR=$HOME/board
export OUSHENG_ACTOR=api-dev

# 1.7 挂 plugin + MCP 配置到代码仓（内嵌资产，幂等；升级后重跑同一命令即同步）
#     + 代码仓 AGENTS.md 追加纪律段（见附录 A）
ousheng adapter install --dir ~/code/admin_api

# 1.8 推上中央仓，其他机器下次 sync 即见
git push
```

协议里的硬锁（CLI 已内建校验的）：agent 的 `--responsible-human` 必须已注册 human 型（问责是人对人的授予，agent 无权创造）。

装完的效果：**opencode 在 `~/code/admin_api` 里写代码，但 session 启动/结束时自动读写 `~/board`**。

> **机器损毁恢复**：re-clone 后重跑同一协议即可（registry 在中央仓，本机只有 me + repos.yaml 两小件）——join 协议兼任灾难恢复动线。

## 4. 阶段 1b：PM 机器安装（可选，更轻）

PM 不碰任何代码仓，不需要 `repo set`。human 身份的 join 只有两步：

```bash
git clone git@github.com:<org>/ousheng-board.git ~/board
cd ~/board && ousheng me pm --name 产品经理    # 未注册则注册 human + 设默认身份
export OUSHENG_DIR=$HOME/board
export OUSHENG_ACTOR=pm              # 窗口以 pm 身份 sync：自动注入 pm 关心的需求单
ousheng adapter install --dir <任意工作目录>
git push                              # 注册推上中央仓
```

PM 若不需要 AI 窗口，也可以直接用终端跑命令，效果相同。

## 5. 阶段 2：日常协作循环

### 执行者总表（谁敲命令）

| 步骤 | 命令 | 执行者 | 触发方式 |
|---|---|---|---|
| 同步 | `ousheng sync` | **plugin 自动** | session 启动 hook |
| 建任务 | `ousheng todo` / `work create` | **AI** | AI 自己调 bash |
| 写代码 | 正常 coding + git commit | **AI** | 正常 AI coding |
| 挂证据 | `ousheng evidence add` | **AI** | 同上 |
| 更状态 | `ousheng work update` | **AI** | 同上 |
| 拍板 | `--ack` | **人（唯一必须）** | 设计如此 |
| 收敛检查 | `ousheng converge` | **AI** | session 空闲 hook 提醒 |
| 推送 | `git push`（上下文仓） | **AI** | 收尾时 |

### 5.1 session 启动（plugin 自动，无人工）

```
session.created → ousheng sync --actor $OUSHENG_ACTOR
  → git pull（拿到其他机器昨晚的变更）
  → 重建索引
  → 注入窗口上下文：「我的队列 + 阻塞 + 相关契约」
```

### 5.2 AI 干活（AI 自己调 CLI）

```bash
ousheng work create --id T-101 --type task --title "实现编排接口" \
  --system admin-api --assignee api-dev --accountable lead   # 建单
ousheng work update T-101 --status doing          # 开工
# ……正常写代码、git commit……
ousheng evidence add T-101 --type git_commit --locator <commit-hash>
ousheng work update T-101 --status done           # 完工
```

> `ousheng todo "标题" --system S` 是**单 human** 时的快捷建单；本指南拓扑含 PM（两个 human），todo 会报 accountable ambiguous，故统一用 `work create`（见 §8）。

发现别的系统引发的问题时：

```bash
ousheng bug report --id BUG-020 --title "编排接口变更导致提交失败" \
  --system admin-api --detected-by data-dev --assignee api-dev
```

责任窗口下次 sync 自动看到，**零通知、零消息系统**。

### 5.3 破坏性变更拍板（人，全天唯一亲手敲的命令）

破坏性契约变更会被 C2 门拦下（AI 无法自批）。流程：

```
① AI 改完契约：`ousheng work show T-101` 读当前内容（记下 revision = N），
   自己生成完整 work item yaml（含 breaking 契约），存为 ack-T101.yaml，
   然后停下告诉你：「需要拍板，文件已备好，revision = N」
② 你在任意机器、任意终端，亲手敲一条命令：
```

```bash
ousheng work update T-101 --file ack-T101.yaml --expect N --ack --actor lead
# → human_ack: {approver: lead} 永久留痕
```

> `work show` 的输出含依赖摘要等附加字段，**不能直接重定向回 `--file`**（严格解码会拒绝未知键）；yaml 由 AI 生成，人只敲最后一条 ack 命令。

产品范围的拍板（做不做/砍不砍）由 PM 执行，同一路径 `--actor pm`。审计上 `approver` 字段永久区分谁拍的板。

### 5.4 session 收尾（plugin 自动提醒 + AI 执行）

```
session.idle → ousheng converge
  → CONVERGED：干净收工
  → IN_PROGRESS：提醒 AI 补 work update / evidence add
  → BLOCKED：明示阻塞项，需要人介入
AI 处理完警告后：git -C $OUSHENG_DIR push    ← 变更飞向 GitHub，其他机器可见
```

## 6. 阶段 3：人看全局（对话式，AI 代跑命令）

你或 PM 对任意 opencode 窗口说一句话即可：

| 你说 | AI 跑 | 说明 |
|---|---|---|
| 「看下全局看板」 | `ousheng view kanban` | 4 系统全看板 |
| 「admin-ui 这周能交付什么」 | `ousheng view system admin-ui` | 单系统视图 |
| 「v2.1 还差多少」 | `ousheng view version v2.1` | 版本验收视图 |
| 「有什么卡住的」 | `ousheng converge` | 跨系统欠账/阻塞检查 |
| 「T-031 砍掉」 | `ousheng work update T-031 --status cancelled` | 砍单 |

**PM 发布需求**（对 PM 窗口说「给 admin-ui 发需求：×××」）：

```bash
ousheng work create --id REQ-101 --type requirement \
  --title "编排页支持批量重跑" --system admin-ui \
  --assignee ui-dev --accountable pm \
  --priority P1 --due 2026-09-30 \
  --description "背景：……；验收标准：1) 批量勾选 2) 失败重试 3) 进度可见"
git push
# ui-dev 机器下次 session 启动自动收到（正文/优先级/截止日随单携带）
```

### 跨系统需求变更与设计方案（design/ 约定）

开发中途需求变更、需要跨多系统整体设计时（系统分散在多台机器不受影响——上下文仓就是汇合点）：

```
1. PM：新建变更单 REQ-2xx，related_to 旧 REQ；按系统拆子任务，depends_on 变更单
2. 设计方案：写 design/2026-09-12-xxx.md 提交到上下文仓（git 即版本管理）
3. 各系统 work item 的 description 引用设计文档路径；涉及接口承诺的，
   contract 呈现在供需双方的单上（kind=http/lib/event/cli）
4. 破坏性变更照旧 C2 门：--ack 拍板后才可动工
5. 所有机器下次 sync 即拿到设计文档与变更单——零会议、零群发
```

上下文仓是普通 git 仓：会议纪要等都可以放。OuSheng 不解析它们——**文档给人读，YAML 给机器读**。方案讨论/技术决策已上绳（v0.4 共识层，见 §7），其余自由文档照旧。

## 7. 治理约定

### 决策权分配（流程约定，落审计留痕）

| 决策类型 | 拍板人 | 命令 |
|---|---|---|
| 产品板（做不做 / 砍不砍 / 优先级） | `pm` | `--ack --actor pm` |
| 技术板（接口破坏 / 数据迁移） | `lead` | `--ack --actor lead` |

### 接口争议的裁决（A 说 A 对，B 说 B 对）

双方**各在自己 work item 上挂 proposed contract**（同一 kind，各自版本）→ 两个竞争提案都在绳上可见 → 依赖方标 blocked → converge 暴露 → 责任人拍板取其一（`--ack`），败方 cancelled 或改 depends_on。系统只保证**分歧可见 + 拍板留痕**，不仲裁——仲裁是替人决策（C3 边界）。

### 权限边界 = git 权限（两档，无需 RBAC）

- **只读 PM**：不给 `ousheng-board` 仓 push 权 → 只能 sync/看板，需求由 lead 代发。
- **全权 PM**：给 push 权 → 可发单、砍单、ack。

### 版本与分支：单主干立场

- **同版本协同**：不切分支。work item 带 `target_version: v2.1`，`ousheng view version v2.1` 跨 4 系统聚合验收。
- **看板不开分支**（反事实推演结论）：若看板按分支拆——PM 发需求必须先切分支；各机器窗口 sync 只见本分支，全局可见性立即破灭；`work/` 同 ID 文件跨分支合并必撞。换来隔离，丢掉全局上下文，与「唯一通讯中心」原则正面冲突，故拒绝。
- 代码仓的分支策略不受影响（各自照旧）；上下文仓恒 main 单主干，版本维度由 `target_version` 字段承载（铁律：revision ≠ target_version）。

### 发布与认领：谁执行、凭什么算完

发布一张单之前问三件事，缺一这张单就是孤儿：

1. **落在哪个系统**（`--system`）——执行、证据验证、架构覆盖都靠它定位；
2. **谁执行**——`--assignee` 指定，或**故意留空当待认领**；
3. **凭什么算完**——按类型的最小信息集：

| 类型 | 必填信息 |
|---|---|
| requirement / feature / task / test | `--description`（验收标准） |
| bug | `--description`（复现 / 期望 / 实际 / 环境）+ `--detected-by` |
| release / deployment | `--version`（target_version） |

**状态就是门槛**：`backlog` 不查（先记账）；`ready` 起查信息；**进行中（`doing`/`testing`/`blocked`）必须有主**——写入路径直接拒；`done` 必须有证据（C1）。无主单在 `ousheng work list --unassigned`（可加 `--system <id>` 过滤）可见，由你或 agent 认领（`view system` 只列进行中的单，不含 backlog/ready 的待认领池）：

```bash
ousheng work list --unassigned                       # 待认领池（PM 巡检）
ousheng work assign T-101 --assignee api-dev --role backend   # 认领（CAS 防并发）
```

agent 的 `context me` **不会**注入无主单——注入面最小化：执行者不需要知道不归他的活。converge 会盯着：进行中无主 = 阻塞，待认领/缺信息 = 警告。

**多系统需求不是一张单**：`designs/` 写方案（`systems:` 列受影响系统）→ `design decide` → 按系统拆 N 张单，各单各有主；单之间用 `depends_on` 表达阻塞，不表达分解。

> **v1 迁移注意**：`ousheng migrate schema` 把 v1 `live` 卡转为 `doing`；若 owner 解析不出（v1 card 无 actor），该单**无主** → converge 直接 BLOCKED（仅 `live` 卡如此；`proposed`/`agreed` 卡落 ready/backlog，无主只是「待认领」警告）。先 `ousheng migrate resolve-owner <id> --assignee A --role R --accountable H` 再 converge。

### 共识层：方案讨论与拍板（v0.4）

线下沟通、整体方案、全局系统信息曾是无绳区——拍板发生在聊天记录里，代码仓里找不到。v0.4 用两个目录收编，**绳只做发现/注入/生命周期，内容人和 agent 直接写文件**：

```
.ousheng/
  architecture/<系统>.md          # 系统全局面貌：零 schema 纯 MD，绳只索引文件名
  designs/<topic>/design.md       # 一个 topic 一个方案（frontmatter 状态机，正文随意写）
  designs/<topic>/round-N.md      # 讨论轮次（节头 `## <actor> — 日期`，机器可读）
```

**流程**：

1. **发起**：任一角色写 `design.md`（`status: draft` + `owner` + `systems` + `related_items`），首版可先放 `round-1.md` 里自己的小节。
2. **讨论**：各角色往 `round-N.md` 追加自己小节（`## <actor> — 2026-09-15`）。draft 方案 × `systems` 覆盖我的作用域 × 最新轮我没发言 → 我的 `context me` 出现 `pending_reviews`——**待发言是派生的，不是登记的**，说完即消失，零元数据腐烂。
3. **拍板**：`ousheng design decide <topic> --actor <human>`。**仅 human**——agent 自 decide = 自拍共识，必拒（同 C2 血统）。
4. **作废**：`ousheng design supersede <topic> --by <new-topic> --actor <human>`（继任者必须存在，禁自 supersede）。

```bash
ousheng design list                              # 全部方案（topic/status/owner/systems）
ousheng design list --waiting-for ui-dev         # 等某角色发言的 draft（PM 巡检用）
ousheng design show csv-export                   # 看方案全文（frontmatter + 正文 verbatim）
```

**converge 共识审计**（BLOCKER：agent 拍板、supersede 环；warning：supersede 悬空/未生效、related_items 悬空、**方案还在 draft 就开工**（doing/testing/done × draft 超前曝光）、architecture 覆盖缺失）。

**注入面铁律**：`context me` 只给指针——`design`（关联单上的方案出处）、`knowledge`（architecture 文件名清单）、`pending_reviews`（待我发言的 topic）——正文自由文本绝不自动注入（免疫面最小化），agent 需要时自己 `design show` / 读文件。`work list` / `view kanban` 不放方案链接（扫视层不放深链接，明文判决）。

## 8. 多 human 注意事项

`ousheng todo` 的 accountable 默认取「唯一 human」。**注册第二个 human（如 pm）之后，`todo` 会报 ambiguous**。此时建单统一改用 `work create`，显式指定 `--accountable`：

```bash
# dev 建技术任务（问责归 lead）：
ousheng work create --id T-101 --type task --title "实现编排接口" \
  --system admin-api --assignee api-dev --accountable lead

# PM 建需求（问责归 pm）：
ousheng work create --id REQ-101 --type requirement --title "批量重跑" \
  --system admin-ui --assignee ui-dev --accountable pm
```

> ID 规则：**前缀 + 系统缩写 + 数字**（`REQ-UI-101` / `BUG-API-020` / `T-SRV-003`）。带系统缩写的原因：离线并发建单没有中央发号器，跨机器撞号靠命名空间隔离——本拓扑一系统一机器，同系统建单只发生在一台机器上，撞号概率归零。真撞了（同 ID 文件）走 rebase 手工解，极其罕见。

## 9. FAQ

**Q：机器之间怎么同步的？**
只有 git push/pull 作用于 `ousheng-board` 仓。GitHub 就是通讯服务器，不部署任何服务端。

**Q：两台机器同时写会不会撞？**
三层防护：本机 `.ousheng.lock`（串行化本机写入，每次写一个 commit）；逻辑并发走 CAS（`--expect` 旧 revision 写入直接拒绝，不会静默覆盖）；跨机 git 层——本机有未 push 提交且远端已移动时，`sync` 的 `git pull --ff-only` 会失败并打印 `pull skipped (...)`，此时按以下流程恢复：

```bash
git -C $OUSHENG_DIR pull --rebase     # 变基追平远端
ousheng sync                          # 重建索引（确认拿到对方变更）
git -C $OUSHENG_DIR push
```

rebase 撞同一 yaml 的情况极罕见（不同机器通常改不同 work item 文件）；真冲突时人工解该 yaml 后 `git rebase --continue`。

**Q：断网/离线能干活吗？**
照常。所有写操作落本地 git 仓，联网后 push 追平；其他机器下次 sync 拉到。

**Q：机器挂了怎么办？**
上下文仓在 GitHub。换台机器 clone、重跑阶段 1（5 分钟）即恢复全部协作状态。

**Q：代码仓被污染了吗？**
零侵入。代码仓多出的只有 `.opencode/plugins/ousheng-sampler.ts` 和 AGENTS.md 纪律段；所有协作数据都在上下文仓。

**Q：AI 怎么知道该跑这些命令？**
两个来源：plugin 在 session 启动/空闲时注入提醒；代码仓 AGENTS.md 的纪律段（附录 A）每次 session 自动生效。

**Q：为什么没有消息通知？**
本体零通知语义（拉取制，三时机）。但 git 托管平台的通知（GitHub watch）是基础设施层赠品，可自行启用——OuSheng 不建通道，也不禁赠品。

**Q：为什么没有燃尽图/统计报表？**
呈现当前状态是绳的本分（kanban/view）；**加工历史是 AI 的活**——历史全在 git，对窗口说「算一下本周燃尽」即可。

**Q：为什么没有评论区？**
对话有归所（你和窗口聊），结论有归所（`--ack` 拍板留痕）。中间态评论制造「看似结论的非结论」。

**Q：为什么没有工时/工作量估计字段？**
绳上只放**可验证或有可审计结局**的事实：due_on 到期可判达成；estimate 永不可证伪。规模自评在对话层完成（progress 的 basis=story-points 已部分承载）。

**Q：能不能用 SQL 直接查协作数据？**
能。`ousheng index rebuild` 生成 `.ousheng/cache/index.db`（SQLite 派生索引、只读镜像），任意 SQL 工具可查。它是加速与外查面，不是事实源——删了随时从 YAML 重建；日常查询默认走内存索引（零基础设施模式）。

**Q：状态标错了 / 单误取消了怎么办？**
都能救，不用碰 git：`done` 单 `work update --status doing` 重开；`cancelled` 单可回 `backlog` 重走（状态机内置重开边）。字段改错直接 `work update`。真灾难（文件损坏）才走 git——canonical state 就是 git 历史，revert 即回滚。

**Q：不同机器装了不同版本的 ousheng 会怎样？**
硬失败而非静默错乱：解码严格拒绝未知字段、`schema_version` 钉死——旧二进制读到新 schema 直接报错，不会静默丢数据。所以**升级要一起升**（各机器重跑 `go install ./cmd/ousheng`）；混跑窗口期协作会卡在报错上，这是特性：宁可失败，不可静默降级。

## 10. 边界：这个系统不管什么

用得好之前，先知道它不管什么。以下不是缺陷，是设计立场（基石 §4 成立边界）。

### 诚实框架，不是真理机器

- C1 门只验「verified 必须挂 evidence」，**不验证据真伪**——恶意或幻觉的 agent 可以编造 `test_result: passed`。系统不撒谎，但不保证别人不撒谎。
- 防线在人：breaking 变更必须 human `--ack`（C2）；accountable human 对 verify/done 拍板。**人不可免审，工具不代替人验货**。
- **注册表是信任锚，也是可伪造面**：agent 机器同样能跑 `team add <id> --type human`——傀儡 human 可让 C2 与 accountable 机械上「合规」（两条命令即可构造"AI 生成→AI 验收"闭环）。系统防**意外**（幻觉自 ack，写入路径已拒），不防**蓄意**。防线在仓外：registry 每次变更都在 git 历史——**人定期 review registry diff，新 human 必须对得上真人**；更硬一档给上下文仓开分支保护/PR review。
- `progress` 是 reported（自称进度），不是实测进度；`activity` 是审计日志，不是事实源。

### 规模边界

- **双人不用绳**：1 人 + 1 个 AI 会话时，对话 + git 就是最好的协调（OuSheng 自身的开发即如此）。绳在 **3+ 并发执行者/多窗口**时才开始挣钱——这正是本指南存在的原因。
- **ID 唯一性 = 前缀约定 + 概率保证**，不是强一致发号。两台机器在同一系统前缀下同时开单撞号，要到 git 合并时才会发现 → 人改一个 ID 再合。同系统同时段高频并行开单时，此机制开始疼。
- **多 human**：`todo` 会报 accountable ambiguous——这是特性不是 bug（机器不猜人），用 `work create --accountable <human>` 显式指定。
- **看板 main-only**：分支上的看板没有全局可见性。要表达分歧，用竞争契约（两张 proposed 卡），不开分支板。

### 实时性边界

所有状态都是 git 文件：断网可用、索引损坏可重建（`sync` 后照旧），代价是**看板所见 = 上次 pull 的世界**。要新鲜就 pull，要实时就不该用这个系统。

## 附录 A：AGENTS.md 纪律段（拷进每个代码仓）

```markdown
## OuSheng 协作纪律

本仓参与多机协作，工程上下文在 $OUSHENG_DIR 指向的上下文仓中。

- 开工：session 启动时 plugin 已自动 sync。先 `ousheng context me` 看自己的
  队列与阻塞，再动手。
- 建单：新工作先建 work item（`ousheng todo` 或 `ousheng work create`），
  开工 `work update <id> --status doing`。
- 证据：done 之前挂证据，例如
  `ousheng evidence add <id> --type git_commit --locator <commit-hash>`。
- 破坏性契约变更：停下，向人说明需要拍板；`--ack` 必须由人亲手执行，
  AI 不得代敲。
- 收尾：session 结束前跑 `ousheng converge` 处理警告，然后
  `git -C $OUSHENG_DIR push`。
- 时机纪律：只在 session 启动 / 遇到问题 / session 收尾时查上下文，
  禁止每轮循环轮询。
```
