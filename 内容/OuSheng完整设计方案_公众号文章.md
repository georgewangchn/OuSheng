# 㸸绳的工程图纸：OuSheng 完整设计出炉，准备开源

> 上一篇文章《我想给 AI Coding 这头黄牛，做一根牵引绳》讲的是"为什么做"——从想造工厂，一路收缩到一根绳。这篇讲"怎么做"——这根绳的工程图纸画完了，目录结构也定了，接下来就是开源、动手、证伪。
>
> 先说名字：项目叫 **OuSheng（㸸绳）**。"㸸"（òu）是河南方言里"牛"的叫法——农村说"放㸸"就是放牛。OuSheng = 㸸（牛）+ 绳（牵引绳）= 套在黄牛鼻子上的那根绳。

---

## 一、一根绳，到底要做什么

上篇说到，OuSheng（㸸绳）的定位是：**一块小看板 + 一套接口标准，协调多个"人 + AI"协作完成软件生产。** 不需要共享记忆、不需要中心验证、不需要 Ontology。

三件薄物件：

1. **看板存储** —— 一个共享 Git 仓，一张卡一个文件，版本/历史/签名白送。
2. **执行器** —— 一个 MCP 服务或命令行，只有 `read_board` / `write_board` 两个动作。
3. **纪律** —— 一份协议文档，规定"何时读、何时写、只发布契约不倒记忆"。

听起来简单。但"简单"不等于"简陋"——把这三件东西做到工程级别，需要回答一堆问题：卡片长什么样？读写怎么防冲突？怎么判断整个项目做完了？依赖关系怎么管？哪些东西该做、哪些东西不该做？

这些问题，就是《OuSheng 完整设计方案》要回答的。**方案已经写完，放在仓库里了，这篇文章是它的通俗版。**

---

## 二、每一件东西，都要过四道关

在设计过程中，我给自己定了一条铁律：**每一个元件都必须过四道关，过不了就删。**

```
新提议
  ├─ 它服务于"跨边界协作必需信息 C"还是"局部实现 I"？ ── I → 拒绝
  ├─ 去掉它，系统还能协作吗？ ── 能 → 非核心，延后
  ├─ 它是"绳"还是"替牛使劲"？ ── 替牛使劲 → 拒绝
  └─ 它破坏 C1/C2/C3 三条防线中任何一条吗？ ── 破坏 → 拒绝
```

这不是装饰性的流程，是真的砍了东西。**最狠的一刀，砍在了自己头上——ASR 被请出了核心。**

ASR 是我之前做的单机多 Agent 运行时，是这个项目的起点。但反事实推演很清楚：去掉 ASR，5 人团队照常协作；AI Coding 工具自己就带写→测→改的收敛环，再建 ASR 等于重造控制器、等于替牛使劲。于是 ASR 从"核心组件"降级成"一个参考示例"。

把自己起家的东西请出核心，有点反直觉。但方案因此更干净、更通用了。

**另一刀砍在了"渐进式上下文披露"上。** 最初设计里允许看板存 Level 0（契约）到 Level 4（原始上下文）五个层级。反事实一推：Level 4 跨界直接撞上第一性原理——"内部状态 I 永不跨界"。裁决：看板永远只存 Level 0（Contract），更高层级的上下文走 owner 节点的按需拉取通道，用完即弃，绝不落板。

这两刀，保住了看板的纯净，也保住了"牵引绳"的自我约束。

## 三、核心设计：一张卡、三个函数、一条状态机

### 卡片 = 接口标准量纲

工具唯一必须做到极致的两件事之一（另一件是把看板呈现清楚），就是把卡片的 Schema 钉死。如同控温前必须先定义"温度"。

一张卡长这样：

```yaml
id: user-auth-api             # 全局唯一标识
owner: backend                # 谁负责这张卡
task: "提供用户登录鉴权接口"     # 一句话意图
status: proposed              # proposed → agreed → live → verified → deprecated
version: 3                    # 乐观锁版本号
depends_on: [db-schema]       # 依赖哪些卡，强制构成 DAG
contract:
  kind: http                  # http | cli | lib | event
  breaking: false             # 是否破坏下游？true 需要人批准
  interface:
    - method: POST
      path: /login
      request:  { body: { email: string, password: string } }
      response: { "200": { token: string, expires_in: int },
                  "401": { error: string } }
      behavior: "有效凭证返回 token；无效返回 401"
evidence:                     # verified 时必填——消费方探针证据
  probe: "POST /login 200 + token 可用"
  passed_at_commit: abc123
  by: frontend                # 谁验证的——消费方，不是生产方自证
human_ack:                    # breaking=true 时必填——人批准破坏性变更
  approver: alice
  at_version: 3
```

每个字段都不是随手加的，都对应一条设计防线：

- **`behavior` 字段 = C1 生死线的落点。** 契约不能只有形状，必须携带行为语义。否则"形状对、语义错"的实现能骗过下游。消费方探针依据 `behavior` 测真实接口。
- **`breaking` 字段 = C2 限速器。** 加法变更 `breaking:false`，agent 自主吸收；破坏性变更 `breaking:true`，必须携人批准，否则写入被挂起。契约变化被强制慢于代码收敛。
- **`evidence` = verified 的准入证。** 没有探针证据，不许写 verified。防止假 verified 污染下游。
- **`depends_on` = DAG 约束的数据基础。** 依赖成环即判 STUCK，交给人打断。

还有一道硬闸门：**未知字段直接拒，超尺寸直接拒。** 结构化的 contract 字段允许（它就是契约），但往里塞源码块、stack trace、memory、调试日志，一律拒绝。skill 可能被忽略，schema 校验不会。**这道门必须落在代码里，不是落在文档里。**

### 三个函数 = 控制论的边界采样

整个执行器只有三个函数：

**`read_board(scope)` —— 读看板。** 纯读，无副作用。每轮工作开始时调一次，采样当前该做什么、依赖有没有变。这就是控制论里的"采样参考信号"。

**`write_board(card, expected_version)` —— 写看板。** 每轮工作结束时调一次，发布产出的契约和状态。四道闸门：
1. CAS 乐观锁（版本不匹配则冲突，防止并发写）
2. Schema 校验（不合规直接拒）
3. 状态机强制（只允许合法迁移）
4. Breaking 限速（破坏性变更需人批准）

**`converge(scope)` —— 算全局状态。** 看板上的纯归约函数，任何节点或人都能在本地算出来，不需要 daemon、不需要中心大脑。三种结果：
- **GLOBAL CONVERGED**：所有契约 verified，无悬空，依赖闭合 → 项目完成
- **GLOBAL STUCK**：有契约卡住、死锁、依赖成环 → 需要人介入
- **IN_PROGRESS**：还在推进中

人看一眼看板，就知道整个协作走到哪了、卡在哪。

### 一条状态机 = 契约的一生

```
proposed → agreed → live → verified → deprecated
```

- **proposed**：任一方都能发起——生产方说"我承诺提供"，消费方说"我需要"。解决冷启动。
- **agreed**：达成一致。仲裁权归契约 Owner，消费方只能提议；分歧上抛人。
- **live**：开始实现，契约成为下游可依赖的参考。
- **verified**：消费方行为级探针通过，确认与现实一致。
- **deprecated**：退场，依赖它的卡被标记需迁移。

诞生、协商、派发、退场，全部在一个字段上闭合，零新机械。

## 四、工具无关：一个 core，多个薄壳

设计方案的核心架构是"一个 core lib，多个薄适配前端"：

```
        ┌──────────────── core lib (Go) ────────────────┐
        │ 存储 · CAS · schema 校验 · 状态机 ·             │
        │ 全局归约 · DAG 检测 · 投影闸门 · 签名验证       │
        └───┬────────┬──────────┬───────────┬────────────┘
        board CLI  MCP server  Claude hook   opencode
       (通用/脚本)  (opencode等) 适配器        plugin 适配器
                                └── 全是薄壳，零重复业务逻辑 ──┘

        store = git 仓（cards/<id>.yaml，version / 历史 / 签名白送）
```

**为什么选 Go？** 单二进制分发、启动快（跨工具高频 shell 调用）、git / yaml / jsonschema 生态齐全。TypeScript 写 MCP 更快，但 Node 启动慢、需运行时依赖，作为裸兜底 CLI 不合适。

**为什么要有 CLI？** 不是所有工具都有 MCP。CLI 是最通用的入口——任何工具、任何脚本都能 shell 调用。它是"零运行时依赖"的兜底。

**为什么 core lib 要独立？** 单一真相源。CLI、MCP、hook 适配器都 import 同一个 core，杜绝多份逻辑漂移。如果各前端各自实现，两份逻辑必然走偏。

**采样保证怎么分级？** 按工具原生能力取最硬档：

| 工具 | 保证硬度 | 机制 |
|---|---|---|
| Claude Code | 硬 | SessionStart hook 强制读，Stop hook 强制写 |
| opencode | 半硬 | plugin 事件触发读写 |
| pi / codex / 人 / 无 hook 工具 | 软 | skill 纪律 + 每周期注入上下文 |

底层都打同一个 core，只是触发机制不同。绳子能套上任何一头牛。

## 五、开源目录结构

方案画完了，代码还没写。但目录结构已经想清楚了——**因为目录结构本身就是设计的一部分。** 一个项目的目录，暴露的是它的架构判断。

```
OuSheng/
├── README.md                     # 项目入口，定位 + 快速上手
├── docs/                         # 设计文档（思考过程的完整记录）
│   ├── 多人AI协作机制_方案基石.md       # 设计原则与逻辑边界
│   └── superpowers/specs/
│       └── 2026-08-09-OuSheng-完整设计方案.md  # 完整产品设计
│
├── 内容/                          # 公众号文章（面向非技术读者）
│   ├── 多人AI协作机制_公众号文章.md      # 第一篇：为什么做
│   └── OuSheng完整设计方案_公众号文章.md     # 第二篇：怎么做（本文）
│
├── pkg/                           # core lib（Go 包，单一真相源）
│   └── core/
│       ├── card.go                # 卡片 Schema 定义
│       ├── board.go               # read_board / write_board / converge
│       ├── schema.go              # 投影闸门（schema 校验 + 尺寸限制）
│       ├── state.go               # 契约生命周期状态机
│       ├── dag.go                 # 依赖图环检测
│       └── converge.go            # 全局收敛归约函数
│
├── cmd/                           # CLI 入口
│   └── board/
│       └── main.go                # board read | write | converge
│
├── mcp/                           # MCP server（import 同一 core）
│   └── server.go
│
├── adapters/                      # 各 AI Coding 工具的薄壳适配器
│   ├── claude-hook/               # Claude Code SessionStart/Stop hook
│   └── opencode-plugin/           # opencode plugin
│
├── skills/                        # 协议纪律（可移植形态）
│   └── board-protocol.md          # 采样律 + 投影律 + 冲突处理
│
├── examples/                      # 参考示例
│   └── frontend-backend/          # 前后端双 agent 单仓验证场景
│
└── go.mod
```

**目录设计的原则：**

1. **`docs/` 和 `内容/` 分开。** docs 是工程文档，给开发者和贡献者看；内容是公众号文章，给产品经理和 CTO 看。两个受众，两种写法，不要混在一起。
2. **`pkg/core/` 是心脏。** 所有业务逻辑只在这里，CLI、MCP、适配器都是薄壳。改逻辑只改一个地方。
3. **`adapters/` 是工具无关性的物理体现。** 每种 AI Coding 工具一个子目录，互不干扰。加一种工具适配，加一个目录就行。
4. **`skills/` 存协议纪律。** 它是一份 markdown，跨工具可移植。不是代码，是规则。
5. **`examples/` 存参考实现。** 第一个就是前后端双 agent 协作场景——OuSheng 要验证的第一个最小场景。

## 六、这套系统不保证什么

设计写到这里，必须诚实地把"不保证什么"写出来。控制论有一条硬边界：

> **你可以完美地跟踪一个错误的参考信号。**

翻译成人话：如果大家一致同意的契约本身是个烂设计，这套系统会让所有人忠实地、一致地收敛到这个烂设计上。**方向对不对，是人和产品的判断，在控制环之外。** 牵引绳只保证牛忠实地往你指的方向走，不替你决定该不该去那儿。

还有两条：

- **`unverified` 的依赖会永久阻挡"项目完成"。** 这是故意的诚实信号——你确实无法确认它能跑，系统宁可如实报告"未验证"，也不谎报收敛。不是 bug。
- **依赖成环即判 STUCK。** 慢且阻尼良好的互依在控制论上未必失稳，但为保持规则简单，一律保守地要求 DAG、把环交给人打断。这是有意识的取舍。

承认这些边界，方案才既完备又诚实。

## 七、先易后难，每步都能跑

设计是完整的最终形态，实现分六步走：

| 阶段 | 目标 | 产出 |
|---|---|---|
| **0 纸面闸门** | 确认 C1 成立 | 目标场景接口可真实探测的纸面确认；钉死 Schema 量纲 |
| **1 core lib + CLI** | 裸兜底可用 | store / read / write / converge + 全部闸门；TDD 全覆盖 |
| **2 MCP + opencode 接入** | 实证三防线 | MCP server；软纪律 skill；实跑前后端双 agent 单仓 |
| **3 半硬采样** | 补齐保证矩阵 | opencode plugin 事件触发；Claude Code hook 适配器 |
| **4 前瞻层** | 鲁棒 + 联邦 | 按需拉取通道、验签、全局看板、deprecation 迁移流 |
| **5 交付** | 最终产品 | 二进制 + 适配包 + 协议文档 + 参考示例；工具无关性证明 |

每阶段可独立运行，末端收敛到完整设计。**不是缩水品，是先易后难。**

## 八、开源

仓库已经建好了：`github.com/georgewangchn/OuSheng`。

**开的就是设计。** 上一篇文章讲的是思考过程，这篇讲的是工程图纸。图纸比代码更值钱——代码是实现，图纸是判断。把判断过程公开，比把代码公开更有价值。

具体来说：

1. **设计文档全公开。** 方案基石（原则与边界）、完整设计方案（数据模型、接口、协议、实现路径），一字不删地放在 `docs/` 里。包括"砍了什么、为什么砍"也写清楚。
2. **目录结构全公开。** 上面那棵树就是最终形态的骨架。贡献者一看就知道东西该放哪、逻辑该改哪。
3. **公众号文章全公开。** 放在 `内容/` 里，面向非技术读者。工程文档和科普文章两条腿走路。
4. **欢迎拍砖。** 尤其欢迎有人告诉我：C1 那条生死线（消费方能否对真实接口做闭环验证），在你们真实的企业网络里，到底成不成立。

上次 ASR 项目吃了"不分享、不先证逻辑"的亏。这次反过来：**先把图纸公开、把逻辑推到别人挑不出洞，再动手写代码。**

## 九、写在最后

从一个"想造工厂"的冲动，到收缩成一根绳，再到画完这根绳的工程图纸——OuSheng 的设计阶段到此收口。

回顾整个思考链：

- **第一篇** 讲的是"为什么"：AI Coding 写得快、人复核跟不上，需要一个最小接触点的协作机制。
- **这篇** 讲的是"怎么做"：一张卡、三个函数、一条状态机，加一个 core lib 和几个薄壳适配器。
- **下一步** 讲的是"能不能跑"：从阶段 0 开始，一环一环验证。

绳子已经画好了，接下来就是把它编出来、套上去、牵着牛走两步看看。

如果你也在做 AI Coding 协作、也在被"多系统对接"折磨、也觉得现有的协作工具太重了——欢迎来 `github.com/georgewangchn/OuSheng` 看看图纸，提提意见。
